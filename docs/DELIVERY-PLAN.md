# 交付与维护架构（指挥官版）

> 这是"上线之后怎么活"的设计稿。R3 的两个 worker（发布 / 运维）照此实现，不得自行改架构。

## 1. 托管形态：GitHub Pages + 仓库子路径

- 站点地址形态：`https://freddywang12138.github.io/<repo>/`
- **关键约束：必须部署在子路径下**，所以：
  - 所有资源引用用**相对路径**（`./assets/...`），禁止以 `/` 开头的绝对路径。
  - 不用 History 路由；首页即单页，`404.html` 指向首页。
- 分支：`main` 是唯一长期分支。`main` 绿 + 自动部署，不搞 develop。

**为什么不用 Vercel/Netlify**：本机没有它们的凭证，要你去开账号授权；GitHub Pages 复用已有 `gh` 登录，零额外授权即可真上线。代价是没有边缘函数和自定义域名（自定义域名需要你自己买）。

## 2. 三个 Workflow 的分工

| Workflow | 触发 | 作用 | 失败意味着 |
| --- | --- | --- | --- |
| `ci.yml` | 每次 PR / push | 静态检查：JS 语法、链接与资源路径、体积预算、HTML 基本校验、单测 | 有 PR 不能合 |
| `deploy.yml` | push 到 `main` | 上传 artifact → 部署 Pages | 线上是旧版本，需立刻处理 |
| `monitor.yml` | `schedule` 每 30 分钟 + 手动 | 探活线上 URL，检查关键资源 200、页面含关键文案、体积未突变 | 线上挂了或被人篡改 |

## 3. 监控怎么"真"起来

纯静态站没有服务端日志，所以监控只能证明**可用性**，不能证明**有多少人用**。这点必须对用户诚实。

- `monitor.yml` 每 30 分钟：`curl` 首页 + 3 个关键资源 + 断言响应体包含特征字符串。
- 连续 2 次失败 → 自动开一个 `incident` 标签的 Issue（如果已有未关闭的就不再重复开）。
- 恢复 → 在该 Issue 上评论"已恢复"并关闭。
- 每周一 09:00 开一个 `weekly-digest` Issue：过去 7 天 workflow 成功率 + 未关闭 incident 数 + 未处理反馈数。

## 4. 反馈闭环怎么落地

- 页面右下角一个"反馈"入口 → 打开预填好的 GitHub Issue 表单（`?template=feedback.yml`）。
- 表单必填：用了什么功能 / 期望 vs 实际 / 设备与浏览器。
- 标签体系：`type:bug`、`type:feature`、`type:ux`、`needs-repro`、`incident`、`weekly-digest`、`good first issue`。
- 每条反馈的流转：`新反馈` → `已复现` → `已排期` → `PR` → `已发布` → `已回复提出者`。**最后一环不能省**，这是"有人管"的证据。

## 5. 可观测性的诚实边界

| 想知道 | 能不能测 | 怎么测 / 替代方案 |
| --- | --- | --- |
| 站点是否可用 | 能 | Actions 探活 |
| 页面是否被篡改 | 能 | 探活断言特征字符串 |
| 有多少访问 | **不能** | 除非接第三方统计（需你注册）或加自建计数接口 |
| 用户在哪个环节放弃 | **不能** | 只能靠反馈表单与 GitHub Issue 间接推断 |
| 压缩效果好不好 | 能 | 本地 QA 用固定样本图做基线对比 |

结论：**"大量真实用户"靠 SEO 和时间，不靠技术。第一周能拿到的真实信号主要是 Issue 和（如果你自己贴到社区）的点击。** 我不会伪造流量数据。

## 6. 迭代节奏

- **每日**：`monitor` 自动跑，我不打扰你；有 incident 才叫人。
- **每周**：`weekly-digest` 自动开工单；我从反馈里挑 1–2 条，走 `工单 → 分支 → PR → CI → 合入 → 自动部署 → 回评提出者`。
- **每次上线后**：指挥官写 3 行复盘（改了什么 / 预期什么 / 下周看什么）。

## 7. 安全与合规

- 页面不收集任何个人信息，不上传图片——这是可被验证的承诺：**DevTools → Network 里不应出现任何指向非本站的请求**（QA 要专门测这一条）。
- Issue 表单提示用户不要贴敏感图片链接。
- 仓库公开，但不在提交里放任何 token/密钥；CI 用 `GITHUB_TOKEN` 最小权限（`pages: write`, `id-token: write`, `issues: write`）。
