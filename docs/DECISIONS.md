# 决策日志（指挥官的拍板记录）

> 只记「有争议、需要裁决、事后可能被追问」的决定。每条写清：谁提的、怎么定的、为什么、代价是什么。
> 目的：避免同一件事反复讨论，也避免后面的人（包括未来的我）不知道当初为什么这么干。

---

## D1 · 单张上限 80MB、单次 60 张、只支持 JPG/PNG/WebP（R1，G1 拍板）

- **冲突**：PRD 写 80MB / 60 张 / 不支持 GIF+AVIF；品牌文案写 50MB / 50 张 / 支持 GIF+AVIF。
- **裁决**：以 PRD 为准，品牌文案已就地修正。
- **理由**：A 类用户（二手卖家）的商品图就是 6–9MB；GIF 动图会被 canvas 弄成首帧、AVIF 解码支持不齐，写上就是无法兑现的承诺。
- **代价**：HEIC/AVIF/GIF 用户会被挡在门外，页面需给出可执行的替代路径（另存为 JPG）。

## D2 · 首版不做 zip 打包（R1，G1 拍板）

- **提案**：PRD 归 P1，品牌文案却写了「全部下载（.zip）」。
- **裁决**：首版逐个下载 + 浏览器拦截降级提示；zip 留给第一个迭代。
- **理由**：zip 要么 vendor 一个库（吃体积预算），要么引入构建；两者都和「零构建、首屏 80KB」冲突。逐个下载的体验损失可控，且能当第一个真实迭代的素材。
- **代价**：批量 12 张时 Chrome 会弹「允许下载多个文件」，需要明确文案兜底。

## D3 · 不做任何匿名上报（R1，G1 拍板）

- **提案**：产品问是否加 opt-in 计数（压缩次数/格式分布/失败率）。
- **裁决**：不加。`track()` 保留为空函数。
- **理由**：隐私是唯一抄不走的差异点，一旦有上报就得解释「不上传图片但上报行为」，叙事立刻变浑；而且没流量时上报也没有统计意义。
- **代价**：首版完全拿不到真实使用形态，只能靠 GitHub Traffic（14 天窗口）和 Issue 反馈推断。

## D4 · 「压到指定大小」不进首版，定为 G5 迭代第一候选（调研提出，我拍板）

- **调研证据**：图好快 5 元/张、压缩图卖会员，都在卖「压到指定大小」；iLoveIMG 的 FAQ 明写不能选压缩比例；TinyPNG 网页版没有目标体积入口。→ 这是**被收费验证过的硬需求**，而 PRD 把它放在 P2，属于范围与需求错位。
- **裁决**：**不打断正在进行的 R2**，把「压到指定大小」写成 G5 第一个迭代需求，且采用折中形态：预设 200KB / 500KB / 2MB + 「最接近值」提示。
- **理由（为什么不在首版做）**：
  1. 通用二分试压每张要 2–5 次编码，PRD 的「10 张 ≤20s」验收会失效，需要重新定基准。
  2. 必须允许「达不到目标」并诚实告知，文案与交互都要新设计，属于独立一轮的量。
  3. 首版先用真实反馈验证「有没有人真的来」，再决定为哪个意图加深度——这比闭门猜需求可靠。
- **代价**：首版吃不到最大的那部分搜索意图，冷启动会慢。

## D5 · 主叙事维持「把图片压小，不必上传」（调研提出，我拍板）

- **裁决**：不押单一方向。H1 同时承担动作词（把图片压小）与差异点（不必上传）；`title` 已覆盖「PNG 转 JPG、转 WebP」的格式长尾。
- **理由**：「压到指定大小」会随 D4 进入迭代；「零上传」是可验证的信任点但不是搜索词；「手机/微信优先」是渠道策略而非首屏叙事，且 iOS 的 WebP 编码能力还需 QA 实测，不能先写进主叙事。
- **代价**：没有一句「为某个具体人群定制」的钩子，转化率上限可能不如精准定位。

## D6 · 隐私承诺的验证方式：CI 静态审计 + 教用户自己看 Network（调研提出，我拍板）

- **裁决**：不引入 Playwright（会带 npm 依赖，破坏零构建与 CI 简洁性）。改用两层：
  1. CI 静态审计：扫描源码中所有 `http(s)://`、`fetch(`、`XMLHttpRequest`、`navigator.sendBeacon`、`new Image(`，只允许白名单（GitHub 反馈链接 + 本站域名）。
  2. 页面文案教用户「打开 DevTools → Network，边压边看」——用户自己能验，比我们自证更硬。
- **代价**：静态审计只能证明代码里没有上报，不能证明第三方库行为；当前零依赖，风险可接受。

## D7 · 托管选 GitHub Pages，但按「可迁移」标准写站（我拍板）

- **已知风险**（调研标注为未联网验证）：GitHub Pages 无 ICP 备案，中国大陆访问可达性不稳定；站点软限制 ≤1GB、带宽软限 100GB/月。
- **裁决**：继续用 Pages（唯一有现成凭证的通道），但要求站点保持 100% 相对路径、纯静态、零构建、无服务端假设。
- **验证方式**：上线后我会从本机（上海）实测首页与资源的响应时间，把「国内可达性」从「猜测」变成「有数据」；若确实不可用，整站可原样迁到任意静态托管，不用改代码。
- **代价**：如果目标是中文用户的自然流量，这一条可能是整件事最大的单点风险，且不是技术能解决的（需要备案域名或境内托管）。
