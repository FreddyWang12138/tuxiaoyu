# 反馈闭环（R3）

> 目标：陌生人 30 秒能提一条有效反馈，我们从收到到回复走完一条完整链路。
> 页面上的「问题反馈」指向 `https://github.com/FreddyWang12138/tuxiaoyu/issues/new?template=feedback.yml`。

## 1. 入口与文件对齐

`?template=feedback.yml` 里的 `feedback.yml` 是文件名，不是 issue 标题。GitHub 只认 `.github/ISSUE_TEMPLATE/` 目录下的文件名，所以三个文件必须正好叫：

| 页面 / 系统要的东西 | 实际文件 | 谁在用 |
| --- | --- | --- |
| `?template=feedback.yml` | `.github/ISSUE_TEMPLATE/feedback.yml` | 页脚「问题反馈」按钮 |
| 报错入口 | `.github/ISSUE_TEMPLATE/bug.yml` | issues/new 的模板选择页 |
| 关闭空白 issue + 兜底链接 | `.github/ISSUE_TEMPLATE/config.yml` | 新建 issue 页面本身 |

改名、加前缀、换目录都会让页脚按钮跳到 404 或空白页。**`feedback.yml` 这个名字不要动。**

提交后表单会自动带上标签：`feedback.yml` → `type:feedback` + `needs-triage`；`bug.yml` → `type:bug` + `needs-repro`。标签要存在才会挂上（见第 5 节建标签命令），不存在时 GitHub 静默忽略，不会报错——所以上线前先把标签建好。

## 2. 标签体系

| 标签 | 什么时候打 |
| --- | --- |
| `type:bug` | 功能做错了：报错、卡住、结果不对。用 `bug.yml` 提的自动带上。 |
| `type:feature` | 现在没有的能力，用户希望加上，比如「想要拖文件夹」。 |
| `type:ux` | 功能没错，但用起来别扭：找不到按钮、文案看不懂、手机上难点。 |
| `type:feedback` | 使用感受、场景描述、夸奖或困惑，不一定是要改代码。用 `feedback.yml` 提的自动带上。 |
| `needs-repro` | 还没被任何人复现过的 bug。复现成功并写下步骤后，换成 `已复现` 状态并摘掉它。 |
| `needs-triage` | 新进来、还没人分类的条目。维护者 48 小时内过一遍，打上 type:* 后摘掉。 |
| `incident` | 线上不可用或大面积失败（页面打不开、批量处理全挂）。优先级最高，先修再归类。 |
| `weekly-digest` | 每周汇总用：把当周新反馈、未回复、超期未处理的条目整理成一条，别单独讨论。 |
| `good first issue` | 范围清楚、改一处就够、不需要熟悉整个仓库，适合第一次参与的人。 |

一个 issue 可以有多个标签，但至少要有一个 `type:*`，并且不能同时挂着 `needs-triage` 和 `needs-repro` 太久——那是没人管的信号。

## 3. 流转状态

每一步都要在 issue 里留痕，靠评论和标签推进，不靠记忆。

| 状态 | 谁做 | 多久内 | 在 issue 里怎么留痕 |
| --- | --- | --- | --- |
| 新反馈 | 系统 + 维护者 | 自动；48 小时内人工看一眼 | 表单自动加 `needs-triage`；维护者回复一句「收到了，我们会在 X 之前给结论」 |
| 已复现 | 维护者或任意贡献者 | 3 个工作日内 | 评论写清复现步骤、浏览器、图片大小张数；摘掉 `needs-repro`，保留 `type:bug` |
| 已排期 | 维护者 | 复现后 5 个工作日内 | 评论写「排进 vX.Y」或「本轮不做，原因：…」；打上里程碑；不做的同时给出替代办法 |
| 已合并 | 提交 PR 的人 | PR 合并当天 | 在 issue 里贴 PR 链接和改动点；issue 保持打开，等发布 |
| 已发布 | 发布负责人 | 合并后下一个部署批次 | 贴 Actions 部署记录链接和线上地址；写清哪个版本、怎么验证 |
| 已回复提出者 | 维护者 | 发布后 24 小时内 | 最后一条评论 @ 提出者，写「已上线，你可以这样验证」，然后关闭 issue |

复现不了也要走完：在第 2 步评论「按你给的信息没复现出来，还差 X」，然后要么请对方补信息，要么按「暂不做」回复并关闭。**停在 `needs-repro` 不动，等于没处理。**

## 4. 回复模板

### 4.1 已修复并上线

```markdown
这条已经修好并上线了。

改的是：<一句话说清改了什么>。
你可以这样确认：<具体操作，比如「重新打开页面，拖 5 张 PNG，进度条会逐张走」>。
线上版本：<部署记录链接>。

如果还遇到同样的情况，直接在这个 issue 里回我，不用重新提。
```

### 4.2 暂不做的理由

```markdown
这条我们这轮不做，说下原因，免得你干等。

原因：<具体约束，比如「批量打包下载要引入 zip 库，会让首屏体积超过 80KB 的预算」>。
现在能用的替代办法：<比如「在结果区点『全部下载』，浏览器会逐张存下来」>。
什么时候可能做：<比如「等首屏体积有富余，或者找到更小的打包方案」>。

这条先关掉。条件变了我们会重新打开，你也可以在这里补一句你的场景，我按需求强度重新排。
```

### 4.3 需要更多信息

```markdown
想帮你定位，但还差一点信息。

需要你补：
1. <具体项，比如「出问题的是第几张，大概多大」>
2. <具体项，比如「点下载时有没有弹出保存框」>

补上之后我按这个顺序查：先按你给的浏览器和图片大小复现，复现出来就排期；复现不出来我再回来问你。
如果方便，开一下开发者工具的 Console，把红字贴过来，比截图更好用（截图里别带个人信息）。
```

三个模板的共同点：不说「感谢反馈」这类空话，不承诺「尽快」，每一条都给一个能当场做的下一步。

## 5. 建标签的命令

上线前在仓库根目录执行一次。`gh` 需要已登录，并且当前目录的远端指向 `FreddyWang12138/tuxiaoyu`。

```bash
gh label create "type:bug"          --color d73a4a --description "功能做错了：报错、卡住、结果不对" --force
gh label create "type:feature"      --color a2eeef --description "现在没有的能力，用户希望加上" --force
gh label create "type:ux"           --color c5def5 --description "功能没错但用起来别扭" --force
gh label create "type:feedback"     --color 1d76db --description "使用感受、场景描述、夸奖或困惑" --force
gh label create "needs-repro"       --color fbca04 --description "还没被复现过的 bug" --force
gh label create "needs-triage"      --color e4e669 --description "新进来、还没分类" --force
gh label create "incident"          --color b60205 --description "线上不可用或大面积失败" --force
gh label create "weekly-digest"     --color 5319e7 --description "每周汇总，不要单独讨论" --force
gh label create "good first issue"  --color 7057ff --description "范围清楚，适合第一次参与" --force
```

`--force` 让同名标签直接更新而不是报错（`good first issue` 是 GitHub 默认标签，一定会撞名）。gh 版本较旧不支持 `--force` 时，去掉它逐条执行，撞名报错不影响后面的命令。

issue 表单里的 `labels:` 只写名字。名字和上面不完全一致（大小写、空格、冒号）就挂不上，改标签时两边要一起改。

## 6. 为什么最后一环不能省

「已回复提出者」看起来最没技术含量，但它决定这个闭环是不是真的闭合：

- 提反馈的人看不到我们的仓库、PR、部署记录。他不收到回复，就只能认为没人管；下次不会再来，也不会告诉别人这里能提。
- 我们自己也拿不到确认。代码合并、CI 绿、部署成功，都不等于用户那边的问题没了。回复里给的验证步骤，是唯一能反过来证明「修对了」的东西。
- 没有回复的 issue 会一直堆在 `needs-repro` 和 `needs-triage` 里。三个月后没人说得清哪条处理过，等于重新捡一遍。
- 公开仓库里，每条被认真回复的 issue 都是一份证据：说明这个项目有人维护。这比任何「欢迎反馈」的文案都管用。

所以规则很简单：**关闭 issue 之前，最后一条评论必须是给提出者的，写清改了什么、他怎么验证。** 自己给自己关的 issue 不算闭环。

## 7. 用户视角的填写样例

一个真实用户从页脚点进来，看到的是这样一份填好的表单（对应 `feedback.yml`）：

```text
标题：[反馈] 批量压 20 张商品图，全部下载要一张张点

你用它做了什么：
把店铺的 20 张商品图压小再上传，图都是手机拍的，单张 6MB 左右。

期望 vs 实际：
期望：压完点一次就能把 20 张全存下来。
实际：结果区只有「下载这张」，得点 20 次，浏览器还一直问保存到哪。
（图没贴，就是普通的白色背景商品图，没有人脸。）

设备与浏览器：macOS Chrome

大概多大的图：单张 6MB，一共 20 张
一次处理多少张：20
输出格式：转 WebP
还想补充的：压完体积确实小了很多，6MB 变 400KB 左右，这点挺好。
```

维护者看到后：打 `type:ux`，摘掉 `needs-triage`，评论复现结论，排期后按 4.1 或 4.2 回复。这条反馈从提交到回复，全程在 issue 里可查。
