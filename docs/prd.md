# Queenfish · PRD（R1）

> 依据 `docs/BRIEF.md` 硬约束编写，冲突时以 BRIEF 为准。本文只定义"做什么 / 怎么验收"，技术方案留给开发轮。
> 版本 v0.1｜产品设计｜G1 待指挥官拍板 MVP 范围

## 0. 一句话

在浏览器里把图片压小、转格式。图片不上传、关掉标签页就消失。**打开 → 拖入 → 拿文件**。

MVP 判定：一个没听过这个站的人，30 秒内把自己 3 张手机照片压到一半以内并下载成功，且全程没有一次上传请求。

## 1. 目标用户

| # | 谁（非技术/半技术） | 在哪 · 为什么 | 失败时会怎样 |
|---|---|---|---|
| A | **二手卖家 / 小店店主**。李姐 42 岁，卖童装，只会用微信和浏览器 | 晚上 10 点，家里 Windows 笔记本 + Chrome；手机拍的商品图传上来，平台限单张 ≤5MB 且只收 jpg，她有 12 张 6–9MB 的图 | 反复换图、被平台驳回，明天上新推迟；或者搜"在线压缩图片"点了广告站，把商品图和身份证一起传上去，卡在"等待处理" |
| B | **学生 / 办公人群**。小陈 大三，要交课程论文；同一路径也覆盖行政发投标材料 | 图书馆，MacBook；8 张实验照片塞进 Word 转 PDF，学院系统限 10MB，23:59 截止 | PDF 超限传不上去；压缩软件要装要收费，还会把图表标注压糊；临截止前手忙脚乱 |
| C | **半技术：前端 / 运营 / 自媒体**。阿哲在写 landing page | 公司 Mac，VS Code 旁边开浏览器；设计给了 20 张 2x PNG，要转 WebP 且控制在 ~200KB/张 | 装 squoosh-cli / imagemagick 卡在依赖；在线工具一次一张，且上传客户素材违反公司规定 |

对 A/B 的硬要求：不注册、不看教程、按钮够大、结果能一次全部拿走。对 C：批量、结果可预期、文件名不乱。

## 2. 核心任务流（3 步，不能再多）

**Step 1 载入。** 界面：整块可点的拖拽区（实为 `<label for>` 包 `input[type=file][multiple]`）、"选择图片"主按钮、一行"支持 JPG / PNG / WebP · 单张最大 80MB"、一行"图片不上传，全部在这台设备上处理"。

**Step 2 确认输出。** 界面：选项条（输出格式 JPG / PNG / WebP / 原格式 + 质量三档 + P1 最长边）、队列行（缩略图、文件名、原体积 → 新体积、状态：等待 / 处理中 / 完成 / 跳过 / 失败）。默认值已填好，不想调的人直接进 Step 3。

**Step 3 下载。** 界面：行内"下载"、底部"全部下载（N）"、P1"打包 zip"。异常：浏览器拦截多文件下载 → 提示"浏览器拦截了自动下载，已改为逐个下载"，并高亮每行下载按钮。

### 异常分支（必须全部实现，且不弹 alert）

| 异常 | 触发 | 界面表现 | 规则 |
|---|---|---|---|
| 格式不支持 | 拖入 HEIC / PSD / GIF / SVG | 不进队列，顶部黄条"已跳过 2 个不支持的文件（HEIC、PSD）。支持 JPG / PNG / WebP" | 不阻塞其他文件；按 name+size+lastModified 去重，同一张拖两次只出现一行 |
| 单文件过大 | > 80MB 或 > 1.2 亿像素 | 该行红字"文件过大，已跳过：124MB > 80MB 上限"；像素超限单独文案 | 硬拒绝，不做半处理（避免标签页 OOM 崩溃）；≥20MB 先黄字提示"较大，处理需要几秒" |
| 压缩后反而变大 | 输出 ≥ 原图 × 0.98 | 行内中性标签"保留原图：压完比原图大 6%"，该行默认下载原图，旁边给"仍要压缩版" | 绝不静默给更大文件；汇总"省了多少"只统计真正变小的行，不虚报 |
| 浏览器不支持 WebP 输出 | `toBlob('image/webp')` 返回类型不是 webp | WebP 选项置灰 + "当前浏览器不支持 WebP 输出，可改用 JPG，或升级 Chrome / Edge / Firefox"；若记住的默认是 WebP，自动回退 JPG 并轻提示 | 检测结果缓存在内存，不重复试；不因此禁用整个工具 |
| 一次拖入 50 张 | 单次选入 50 张（超过 60 张上限时） | 50 张全部入队；超 60 时顶部提示"已加入 60 张，另有 N 张未加入"。列表可滚，进度 N/50，可"取消剩余" | 并发 `min(4, hardwareConcurrency - 1)`，完成一张回填一张；全程主线程不冻结 |

## 3. 范围

### P0（首版必须有，每条都能被验）

| # | 功能 | 验收标准 |
|---|---|---|
| P0-1 | 拖入 / 选择多张 JPG / PNG / WebP | 拖 5 张 → 队列 5 行；Tab 到拖拽区按回车能弹文件框；同一张选两次只一行 |
| P0-2 | 压缩并输出 JPG | 3MB JPG 用均衡档 → 输出 ≤ 原 70%；5 张样本人工对照，100% 缩放下无可见色块/涂抹感；系统看图器能打开 |
| P0-3 | 输出 WebP（支持时） | 同一张图 JPG / WebP 各出一份，WebP 更小且 Chrome 能打开；`file.type === 'image/webp'` |
| P0-4 | 质量三档（体积优先 / 均衡 / 质量优先） | 三档跑同一图，体积单调递增（容差 ±2%）；切档对已完成行的处理要明确（标"需重新处理"或自动重算，二选一写死在代码里） |
| P0-5 | 批量队列 + 进度 + 取消 | 10 张 3MB JPG 全部完成 ≤ 20s（4 核 8GB），期间页面可滚可点；"取消剩余"后未开始行变已取消，已完成行保留 |
| P0-6 | 结果对比 + 单张下载 | 每行显示原名、原→新体积、节省 %、像素尺寸；下载文件名 = 原名 + 目标后缀，落盘可打开 |
| P0-7 | 全部下载 | 逐个触发下载；被拦截时有可见提示与替代路径 |
| P0-8 | 隐私：零上传 | DevTools Network 全程无第三方域、无任何图片上传请求；页面加载后断网仍可完成一次压缩 |
| P0-9 | 照片方向正确 | 含 EXIF Orientation=6 的手机照片，输出方向与相册一致（不躺倒） |
| P0-10 | 输出剥离 EXIF | 用 exiftool 检查输出无 GPS / 机身型号；页面写明"输出图不含原始拍摄信息" |
| P0-11 | 无障碍 | 全流程仅键盘可完成；focus 可见（对比 3:1 以上）；进度用 `aria-live="polite"` 节流播报；每个按钮有可读名称 |
| P0-12 | 性能与埋点预算 | 首屏 HTML+CSS+JS 未压缩合计 < 80KB；首屏无阻塞网络请求；`track()` 是空函数、默认不发任何请求 |

### P1（首版之后第一个迭代）

批量打包 zip（依赖 vendored 到 `assets/vendor/`，≤ 15KB）；最长边缩放（只缩不放，预设 1920 / 1280 / 800）；前后并排预览；记住上次设置（localStorage）；行级单独覆盖全局档位；文件名后缀规范化（`-compressed` / `-webp`）。

### P2（记录，不做）

目标体积模式（"压到 200KB 以内"，质量二分最多 5 轮）；文件夹拖入递归；PWA 离线；GIF 首帧 / SVG 栅格化 / AVIF 输出探测；高级参数折叠（自定义质量数值、元数据保留开关）。

### 首版明确不做

| 不做 | 理由 |
|---|---|
| 上传 / 云端存储 / 账号 / 历史记录 | 违反硬约束 2。一旦有服务端，"不上传"这张唯一的差异牌就打不出去 |
| 远程 URL 导图 / 从链接抓图 | 需跨域 fetch 且多数站点不放行；形态上等于"把别人的图拉过来"，隐私叙事变模糊 |
| HEIC / AVIF / RAW 输入 | 浏览器原生解码不齐（HEIC 基本只有 Safari 认），要引 wasm 解码器，与零依赖、首屏 80KB 直接冲突 |
| GIF 动图 / 视频压缩 | canvas 只能取首帧，动图重编码要额外编码器；做出来只是个"会弄坏 GIF 的转换器" |
| AI 去背景 / 超分 | 要下载 MB 级模型，与首屏预算和零依赖冲突 |
| 连续质量滑块、色度子采样、渐进式等高级参数 | 认知成本高且给不出可解释预期；三档预设覆盖绝大多数场景 |
| 多语言、多余皮肤 | 搜索意图是中文，先把一件事做对 |
| 第三方统计 / 广告 | 硬约束 5，也会让"隐私"这句话不自洽 |

## 4. 页面区块结构（上 → 下）

| 区块 | 内容 | 这块要达成什么 |
|---|---|---|
| 1 顶栏 | 品牌名 + "图片压缩 / 格式转换，不上传" + 隐私徽标 | 3 秒内让人相信"我的图不会离开这台电脑" |
| 2 主操作区 | 拖拽区（含"选择图片"）+ 支持格式与大小一行 + 本地处理一句话 | 0 学习成本开始；键盘用户第一步就有着落 |
| 3 选项条 | 输出格式 + 质量三档 +（P1）最长边 | 默认即可用；想调的人 2 次点击内找到 |
| 4 结果列表 | 缩略图、文件名、原→新体积、节省 %、状态、下载 | 批量时每张图的账都看得见，出错能定位到具体行 |
| 5 汇总条 | "12 张 · 38.4MB → 9.1MB" + 全部下载 | 一次拿走全部结果，不用逐行点 |
| 6 说明区 + 页脚 | 3 条 FAQ（为什么没变小 / 安全吗 / 支持什么）+ 无追踪声明 | 拦掉三类高频疑问，减少困惑跳出 |

布局：单列主流程，内容最大宽 ~880px；≤720px 时列表由行式表格转卡片；触摸目标 ≥ 44×44px；选项条在空状态隐藏，有第一张图后才出现（出现时不顶开拖拽区，避免误点）。

### 三种界面形态

- **空状态**：只有区块 1、2、6。拖拽区是页面最大元素（≥ 320×200 虚线框），中间"把图片拖到这里，或选择图片"，下方一行"支持 JPG / PNG / WebP · 单张最大 80MB · 图片不会上传"；初始焦点在"选择图片"按钮；没有空表格、没有灰掉的结果区。
- **处理中**：列表出现；汇总条变"处理中 3/10" + 进度条 + "取消剩余"；行内 spinner + 队列序号；`aria-live` 每完成一张播报一次（节流合并，不逐帧）；主按钮禁用防重复入队，拖拽仍可加，追加到队尾；滚动保持 60fps。
- **结果对比**：汇总条变"12 张 · 38.4MB → 9.1MB（省 76%）"+ "全部下载"；行内原体积用次要色/删除线，新体积用主色，附节省标签；变大行显示"保留原图 + 原因"；失败行显示可读原因 + "重试"；0 张成功时汇总条改为"这次没有生成文件，原因见上"，不显示空汇总。

## 5. 成功指标

**先说实话：没有后端，就没有真实访问量。** 别把 star 当流量。

### A. 端内可测、无需上报（首版就靠这些判断"做得对不对"）

| 指标 | 怎么量 | 目标 |
|---|---|---|
| 首屏字节 | 统计 HTML+CSS+JS 未压缩体积 | < 80KB |
| 首屏请求 | DevTools Network（禁用缓存） | 只有本站静态资源，0 个第三方域 |
| 10 张处理时长 | 固定样本 10×3MB JPG 本机计时 | ≤ 20s，且无 > 50ms 长任务 |
| 中位节省率 | 10 张样本 原/新 体积比 | 均衡档 ≥ 40% |
| 变大兜底覆盖率 | 构造一张已高度压缩的小图 | 100% 出现"保留原图" |
| 输出正确性 | 像素尺寸、EXIF 剥离、方向、透明 | 逐项人工 + 脚本核对通过 |

这些是"我们验证自己"，不是"用户行为"。

### B. 端内可测、但要聚合就必须上报（受硬约束 5 限制，首版默认关）

能算但拿不到的数：压缩次数、输入/输出格式分布、质量档分布、批量规模分布（1 / 2–9 / 10+）、取消率、失败原因分布、变大比例。

- 现状：`track()` 只有空实现，首版不产生任何上报，所以这些数只能在本机自己试出来，**不代表真实用户**。
- 将来若要，也只能做"用户点一下才发"的 opt-in，且发计数不发图片（留给指挥官决策）。
- 局限：opt-in 必是自选小样本，只能看方向，不能算比例。

### C. 必须有后端或平台侧权限才能测 → 首版拿不到

访问量 / UV / PV、来源渠道、搜索词、新老用户、留存、完整转化漏斗、真实崩溃率、设备分布。

### D. 近似推断方案与局限

| 近似手段 | 能推断什么 | 局限 |
|---|---|---|
| GitHub Traffic API（views / clones，14 天滚动） | 是否真有人来、大致量级 | 只有 14 天窗口、无来源无设备；clones 含 CI 与爬虫；缓存命中会少算 |
| GitHub issue / 用户邮件反馈 | 真实痛点与失败场景 | 沉默的大多数不可见；一条吐槽不能当比例 |
| 关键词工具（Keyword Planner、百度指数）估"图片压缩""png 转 jpg" | 需求存在与季节波动 | 那是搜索量，不是本站流量，不能拿来汇报"我们有多少用户" |
| star / fork / release 下载 | 兴趣代理 | 极易被单次曝光放大，不作 KPI |

统一口径：对外只说可验证的工程指标（首屏 80KB、零上传、单张耗时），不说"日活/访问量"。任何"XX 人在用"必须有平台数据支撑，否则不写。

## 6. 三个关键取舍

**1) 单张优先还是批量优先 → 单张优先做深，批量在同一界面里天然成立。**
搜索意图和首次使用绝大多数是 1–2 张；批量是卖家和办公的"第二需求"，但它决定留存。做法：默认视图就是单张也能走完的流程，底层队列从第一天就是数组（1 张 = 长度 1 的批），所以不为批量做单独页面、任务中心、文件夹递归、断点续传。代价：一次 200 张这种极端场景不优化，单次上限 60 张，并写在界面上。

**2) 是否自动选格式 → 不做"暗自动"，做"有理由的默认值 + 一行可见说明"。**
规则：JPG 进 → 默认 JPG；PNG 无透明 → 默认 JPG；PNG 有透明 → 默认 WebP，不支持则留 PNG 并提示"转 JPG 会丢透明、变白底"；WebP 进 → 默认 WebP。理由：自动一旦出错（透明变白底、动图变静图），用户无法归因，只会觉得"这工具坏了"；显式默认让他看得见、改得动、错了找得到原因。代价：多几行 UI 文案，且要维护一小段 alpha 采样检测。

**3) 要不要质量滑块 → 不做连续滑块，做三档预设；自定义数值放 P2 折叠。**
普通用户不理解 q=0.78；滑到 30% 糊了，是我们让他糊的。三档能给每档一句人话（体积优先"适合有上传大小限制"、均衡"日常够用"、质量优先"图表文字多选这个"），可测、可回归。代价：专业用户觉得不自由，用 P2 高级折叠兜住，不进首版。

## 7. 文案与红线（给开发 / 文案）

- 禁用："最快""第一""无损""一键瘦身 90%""永久免费"等无法自证的表述；不承诺压缩比，只显示"这次实际省了多少"。
- 必须出现："图片不会上传，全部在你的浏览器里处理。"
- 继承 BRIEF：零构建、无后端、Web Worker、依赖 vendored、`track()` 空实现、无追踪脚本、键盘可达。
